VSTODO · GIT INTEROPERABILITY

Try VSTodo without throwing away your Git repository.

You do not need to delete .git, clone everything again, or abandon your existing GitHub remote to explore VSTodo. Run vstodo adopt to create a separate .vstodo/ repository beside Git and import supported repository data.

THE SAFETY MODEL

Git stays in place.

VSTodo stores its own metadata in .vstodo/. During adoption, it reads the existing Git object database and refs, preserves copies of .git/config and .git/index under .vstodo/migration/, and adds a local exclude rule so Git does not report VSTodo's metadata as untracked.

The original Git objects, refs, config, index, remotes, and working files are not rewritten by adoption. Existing Git commands remain available while you evaluate VSTodo.

GET STARTED

Adopt an existing working tree

  1. Start in the root of your existing Git repository

    Make sure important work is recoverable. VSTodo currently accepts standard .git directories using SHA-1 object IDs.

  2. Run the adoption command

    vstodo adopt

    VSTodo imports loose and packed Git objects, branches, tags, remote-tracking refs, HEAD, remote URLs and fetch settings, upstream settings, and local user identity.

  3. Inspect the imported repository

    vstodo status
vstodo log
vstodo remote -v
vstodo fsck

    Check the branch, history, remotes, and object integrity before creating VSTodo commits. Existing Git staged changes are preserved in the saved Git index snapshot, but are not automatically staged in VSTodo.

  4. Use VSTodo for new local work

    vstodo add README.md
vstodo commit -m "Update documentation"

    VSTodo writes its own objects and refs under .vstodo/. Adoption does not remove or rename your Git repository.

  5. Connect to the existing remote when you choose

    vstodo fetch origin
vstodo push origin main

    Existing HTTP(S) remote settings are imported. GitHub authentication can be supplied through VSTODO_GITHUB_TOKEN or GITHUB_TOKEN. Push is fast-forward-only; force pushes, tag pushes, and multi-ref pushes are not currently supported. Inspect local and remote history before publishing.

MOVE CHANGES BACK TO GIT

Keep a clear path back

To place VSTodo-created commits into the currently checked-out Git branch, run this explicit export command from the adopted working tree:

vstodo export-git

Export writes missing Git-compatible objects and advances the matching Git branch using a lock-file compare-and-swap update. It refuses detached Git HEAD, branch mismatches, locked refs, corrupt objects, and non-fast-forward history. It does not modify the Git index, config, working files, remotes, or remote history. Use ordinary git push when you decide to publish the exported commits.

Important: This is an explicit export, not automatic two-way synchronization. Git-side commits made after adoption are not automatically watched or reconciled into VSTodo. Do not switch back and forth by editing the same branch in both tools without checking their histories.

CURRENT LIMITS

Know what adoption supports today

  • Standard Git working trees with a .git directory and SHA-1 object IDs.
  • Linked worktrees, submodules, SHA-256 repositories, and object alternates are rejected safely.
  • HTTP and HTTPS remotes are supported by VSTodo transport. SSH settings can be preserved, but VSTodo cannot use SSH transport yet.
  • Existing staged changes are backed up with the Git index snapshot; they are not imported as VSTodo staged changes.
  • Remote push currently supports one fast-forward-only branch update; force, tag, and multi-ref pushes are not supported.

These are implementation limits, not promises of complete Git compatibility. Check the VSTodo README and command reference for the current state before using it on important repositories.
