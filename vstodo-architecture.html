VSTODO · SYSTEM DESIGN

How VSTodo is put together.

VSTodo is an independently implemented version-control system in Go. Its implementation uses Git-compatible object serialization and a supported subset of Git smart-HTTP for interoperability; it does not copy Git's source code.

Command and library layers

The command-line interface dispatches commands to focused handlers. Each handler uses the application context to access repository discovery, object storage, the staging index, and references. 

CLI command
    ↓
command handler
    ↓
internal/app.App
    ├── repository root and metadata
    ├── object and pack storage
    ├── staging index
    └── HEAD and reference store

The library packages live under internal/; command handlers live at the module root. The project currently uses the Go standard library without third-party runtime dependencies.

Git-compatible object model

Core objects are addressed by the SHA-1 of their canonical type, size, and content envelope. The supported object types are:

Object Stores Role
Blob Raw file bytes File content
Tree Mode, name, object ID entries Directory snapshot
Commit Root tree, parents, identities, message Versioned snapshot and history
Tag Target object, tagger, message Annotated reference 
<type> <size>\0<content>

Using the same core object encoding makes supported loose objects and packfiles readable by Git tooling. It does not make VSTodo a complete Git implementation.

Storage and references

  • Loose objects: immutable, zlib-compressed files under .vstodo/objects/, published atomically.
  • Pack storage: validated Git-compatible packfiles and version-2 indexes; fetch publishes the pack and index before advancing remote-tracking refs.
  • Index: a Git DIRC version-2 staging index with checksums, file modes, lock-file publication, and stale-snapshot protection.
  • References: HEAD, branches, tags, and remote-tracking refs stored separately from the object database, with lock-file and compare-and-swap updates.

Pack lookup currently decodes a complete pack to resolve objects and deltas. Large-pack random access and repacking remain scalability work.

Remote transport

The HTTP transport implements reference discovery and the fetch, clone, pull, and fast-forward-only branch push flows needed by current workflows. Credentials are supplied through environment variables rather than embedded in remote URLs.

Force pushes, tag pushes, multi-ref pushes, SSH transport, and full Git protocol/configuration compatibility are not currently supported.

Git adoption and synchronization

Adoption creates a separate .vstodo/ metadata directory beside a supported .git/ directory. Git objects and refs are imported; copies of Git's config and index are preserved. Git remains available throughout the process.

  1. vstodo git-status compares the current Git and VSTodo branch tips without changing repository state.
  2. vstodo sync-git imports Git objects and fast-forwards the matching VSTodo branch only when Git is ahead. A Git branch lock and VSTodo compare-and-swap protect the update.
  3. vstodo export-git is the explicit reverse operation for exporting VSTodo-created commits into the checked-out Git branch.

These commands reconcile committed branch history only. They preserve both indexes and the working files; they do not import Git's staged or unstaged changes. Diverged histories are rejected rather than resolved automatically.

Current compatibility limits

  • SHA-1 object IDs only; SHA-256 repositories are not supported.
  • Adoption requires a standard .git directory. Linked worktrees, submodules, and object alternates are rejected.
  • HTTP and HTTPS remote transport is supported; SSH remote settings can be preserved but are not usable by VSTodo transport.
  • Git hooks, reflogs, all index extensions, complete config semantics, and every Git transport capability are not implemented.
  • Pack maintenance and bounded-memory random access remain outstanding.

Check the source repository for the implementation state of a command before using it in a critical workflow.
